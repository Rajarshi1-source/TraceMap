Implementation note

The zero-blame edge is present in the returned dict with value 0.0, not omitted — verified. The map needs the row to fade the edge out rather than drop it. Copy the algorithm verbatim and do not tidy it: the kid.end_ns <= span.start_ns guard, the max(kid.start_ns, span.start_ns) cursor move and the final segments.reverse() are each load-bearing for at least one test.

Cycle safety — proven, not assumed

A worker that hangs on a malformed trace is worse than one that crashes. A parent-pointer cycle cannot hang the walk, and the reason is structural: every span has exactly one parent, so a cycle forms a component containing no orphan; _walk is entered only from an orphan root, making cycles unreachable. Empirically a two-span cycle returns []. Do not add a cycle guard — it would be dead code implying a risk that does not exist.

Recursion depth

With the limit lowered to 300, a 400-deep chain raises RecursionError inside compute_critical_path, which the assembler already catches. Depth 150 completes cleanly. At the default limit the failure boundary is ~400 spans in a chain — far beyond a five-service demo.

02 Findings that change the build

Four findings. The first two are material and must be fixed before the schema and assembler are written — cheap now, expensive in week 6.

F1 · blocking  Roll-up counters are not aggregated on merge

service_edges_1m and service_red_1m are AggregatingMergeTree tables whose counters are declared as plain columns:

ENGINE = AggregatingMergeTree
ORDER BY (source_service, target_service, time_bucket)
--
request_count    UInt64,                                 -- plain column
error_count      UInt64,                                 -- plain column
crit_ms_sum      SimpleAggregateFunction(sum, Float64)   -- correct

AggregatingMergeTree collapses rows sharing a sorting key and merges only aggregate-function columns. A plain column keeps one arbitrary value. The incremental MV fires once per insert block, so one minute receives many rows with an identical sorting key — and on merge, all but one request_count is discarded.

The symptom is exactly what Rev 3 §4 exists to prevent: no error, and a dependency map that quietly under-counts under load. error_rate — a ratio of two independently mangled counters — is wrong in an unbounded direction. This is the same defect class Rev 3 caught in Rev 2, one layer further down. That crit_ms_sum is correct in the same statement shows the pattern was known and simply not applied to the counters.

Fix, both roll-up tables:

request_count    SimpleAggregateFunction(sum, UInt64),
error_count      SimpleAggregateFunction(sum, UInt64),
Verified 2 Sep 2026 · ClickHouse 26.3

Run twice against the real MV and roll-up table — three inserts into one minute for one edge, one of them an error:

Worse than predicted. The error count collapses to zero, and error_rate in Q1 is a ratio of two independently mangled counters — so red edge colouring would never fire. The demo would show a healthy green graph while payment-svc returned 5xx.

Fixed in all three documents and in the tracemap-clickhouse-analytics skill, which now carries the rule, the measured table, and a prohibition line.

F2 · blocking  Duplicate spans corrupt the assembler, not just percentiles

Rev 3 and the ClickHouse skill both decide to accept duplicate spans because "a duplicated span shifts a p99 imperceptibly." Sound for percentiles over raw spans. It does not hold for the derived path — and the assembler is on the derived path. Reproduced with two spans sharing a span_id:

edges: {('gw', 'svc-b'): 85.0}     # the ('gw','svc-a') edge vanished entirely
  1. by_id collides. The last duplicate wins, so a span's service and timings are silently replaced and blame moves to a different edge.
  2. The edge-row loop iterates spans, not by_id. A duplicate emits two rows into trace_edges, double-counting the edge and feeding its duration into the TDigest twice.

Fix — dedupe at the assembler's fetch boundary. One clause, and the "accept duplicates in raw storage" decision stays intact:

SELECT trace_id, span_id,
       argMax(parent_span_id,        timestamp) AS parent_span_id,
       argMax(service_name,          timestamp) AS service_name,
       argMax(start_time_unix_ns,    timestamp) AS start_time_unix_ns,
       argMax(end_time_unix_ns,      timestamp) AS end_time_unix_ns,
       argMax(status_code = 'ERROR', timestamp) AS is_error
FROM tracemap.spans
WHERE ...
GROUP BY trace_id, span_id          -- the fix

This sharpens the interview answer rather than weakening it: "I accept duplicates in raw storage because dedup costs merge CPU forever and moves a p99 imperceptibly — but I dedupe at the assembler boundary, because there a duplicate doesn't nudge a percentile, it silently reassigns blame to the wrong edge."

F3  One line sits outside the recursion guard

attribute_to_edges recurses in _depth() at the same tree depth but is called outside the assembler's try/except RecursionError. Nearly unreachable in practice, since compute_critical_path runs and fails first. Cost of fixing: moving one line inside the guard.

F4  Reference documents are duplicated

Three documents exist at the root and inside .skill archives, byte-identical today. Editing either copy creates a silent fork. See decision D4.

Found while building — Phases 0–1

Three environment defects the documents did not anticipate. All are fixed in the repository; the first two contradict what starter-code.md still says.

F5  PostgreSQL 18 moved its data mount

starter-code.md §3 mounts the volume at /var/lib/postgresql/data. On PostgreSQL 18 the container refuses to start:

Error: in 18+, these Docker images are configured to store database data in a
       format which is compatible with "pg_ctlcluster" ... there appears to be
       PostgreSQL data in: /var/lib/postgresql/data (unused mount/volume)

18+ expects a single mount at /var/lib/postgresql, storing data in a major-version subdirectory so pg_upgrade --link works without crossing a mount boundary. Fixed in compose; starter-code.md should be corrected before Phase 3 copies from it.

F6  asyncpg has no Python 3.14 wheel

pip install asyncpg on python:3.14-slim falls back to a source build and fails with error: [Errno 2] No such file or directory: 'gcc'. Adding a compiler to the runtime image is the wrong fix — it inflates both the image and the CVE surface for a build-time need.

Both Python services now use psycopg[binary,pool] 3.2.10: ships wheels, first-class async, slim image. The bounded pool is the bulkhead the plan already calls for.

F7  The Go build was not reproducible

The first Dockerfile ran go mod tidy at build time with no committed go.sum, so every build resolved versions afresh. Both files are now committed and the build runs go mod download, verifying against recorded checksums.

Not a defect, but worth writing down

GNU make is not bundled with Git for Windows, and the Makefile is the interface every phase's exit criteria are expressed in. winget install ezwinports.make provides it.

06 The project's own critical path

Fitting, given the subject. What genuinely blocks what.

P0 bootstrap └─► P1 services ──────────────────────────────┐ │ (M1 concurrent fan-out) │ ▼ │ P2 instrumentation ─────────────────┐ │ │ (M24 service.version) │ │ ▼ │ │ P3 ClickHouse ──► P4 CRITICAL PATH ─┴──────┴──► P5 dashboard │ │ ▼ ▼ P6 detector ──────────────► P7 eval + deploy │ │ └──────────► P8 docs ◄────────┘

The hard chain is P1 → P2 → P3 → P4. Everything that makes this project different lives downstream of Phase 4, and Phase 4 is worthless if M1 was violated in Phase 1. That is why the fan-out check appears as an exit criterion in both Phase 1 (in code) and Phase 2 (visually, in Jaeger).

What can run in parallel

  • k6 scripts, any time after the endpoints are named
  • Helm chart and Dockerfiles, during P5/P6 dead time
  • ADRs 0001–0004 belong in the phase that earns them, not batched into week 8. An ADR written eight weeks later reads like one
  • docs/LIMITATIONS.md belongs in P4, while the caveats are fresh

What cannot: the 12 eval cases must run sequentially, and the detector cannot be tuned before P4 produces critical_ms.

08 Decisions — resolved

All five decided. D1 was settled by running the check; the other four are called below with their reasoning, so nothing blocks the build.

D1 Verify F1 before writing the schema? done

Verified on ClickHouse 26.3. F1 is real, the fix is correct, and all three documents plus the skill are rectified.

D2 Host sizing Hetzner CX32

Commit to CX32 — 4 vCPU / 8 GB / ~€7.05 per month. Oracle stays a documented alternative, not the plan.

1. Oracle's free ARM tier is a capacity lottery, worst in the regions nearest this project — a demo that must work on interview day cannot depend on winning it. 2. ARM means verifying a multi-arch path for every base image, ClickHouse and the collector; that is real work bought with "free". 3. €8/month is a better README line than €0 — it is the number that makes the cost meter land.

⚑ The consequence you must accept: 8 GB against a ~7 GB floor is 1 GB of headroom. So this comes with a binding condition — Prometheus and Grafana move to the full profile and are not resident during the core demo, returning ~1.0 GB. If you later want them always-on, the honest answer is CX42 at ~€14, not wishful thinking about the floor.

D3 Stretch differentiators D5 + D6

Cost meter and edge-level SLOs. This changes my earlier recommendation of D5 + D8.

Both D5 and D6 are largely assembly of things Phases 3 and 7 already build; D8 is net-new infrastructure with an upstream that warns of breaking changes between minor releases.

Marginal costReusesRisk
D5 cost meter1–2 dClickHouse system.parts, collector metrics already scrapedLow
D6 edge SLOs2 dThe burn-rate rules already written in Phase 7Low
D8 eBPF/OBI2 d nominalNothingHigh pre-1.0, privileged DaemonSet on one node

D6 is also the better story: an SLO on critical-path latency per dependency edge is a direct extension of the flagship, not a feature bolted on — and no OSS tool does it. D8 drops to future work; the Go honesty story does not need it, since M11's framing is a claim about where the ecosystem is going and is fully creditable without shipping a pre-1.0 DaemonSet. Week 8 has zero slack.

D4 Duplicated reference docs root is authoritative

The three root documents are the source; .claude/skills/*.skill become generated build artifacts. This reverses my earlier recommendation.

I changed my mind because I watched the failure mode happen in this session: fixing F1 meant editing the root file and then remembering to copy it into the skill directory and repack. An invariant that depends on remembering is not an invariant.

The deeper reason: a zip cannot be reviewed. A .skill archive does not diff in a pull request, cannot be commented on line by line, and hides its own drift. Source of truth belongs in text that git can show.

skills/<name>/SKILL.md        ← source, diffable, reviewed
schema-and-queries.md         ← source, single copy
eval-harness.md               ← source, single copy
starter-code.md               ← source, single copy
        │  make skills
        ▼
.claude/skills/<name>.skill   ← build artifact

CI re-runs make skills and fails if the working tree changes, which makes staleness impossible to merge — the same discipline as a committed lockfile.

D5 Eval-gate scope 4-case smoke on PRs

A 4-case smoke tier on PRs touching detector paths; the full twelve nightly on main.

45 minutes on every PR trains you to route around CI, and a gate people avoid is worse than no gate. The earlier framing had the smoke tier as a fallback if behind — that is backwards. It is the right design regardless of schedule.

CaseCovers
001_null_baselineFalse positives — the measurement everyone forgets
006_parallel_decoyThe flagship; a wall-clock detector fails it by design
003_payment_latency_60msLatency sensitivity, the canonical brief case
007_payment_errors_10pctThe error path

≈12 minutes, and it still fails a deliberately broken detector — which is what Phase 7 criterion 5 must demonstrate. Any score you quote must name its tier.
